# Сети: локализация по слоям

Начни с направления потока: откуда выполняется запрос (конкретный Pod/узел/клиент), куда (имя/IP/Service), протокол/порт, точная ошибка и время. При отсутствии ключевого параметра запроси его. Проверка с другого узла не доказывает доступность из исходного Pod.

1. **DNS.** Различай NXDOMAIN, SERVFAIL и timeout. Проверь имя/FQDN, namespace, search/ndots, A/AAAA и доступность DNS по UDP/TCP 53; затем состояние/логи CoreDNS и его доступ к API, если это относится к ошибке. Не объявляй CoreDNS причиной до локализации. Резолвинг имени не доказывает доступность TCP/HTTP.
2. **Service и endpoints.** Различай Pod IP, виртуальный ClusterIP, NodePort, LoadBalancer и Ingress/Gateway. Сверь protocol/port/targetPort, selectors и готовые адреса EndpointSlice/Endpoints. Наличие записи endpoint не доказывает сетевую достижимость. При отсутствии ready адресов сначала проверь backend Pods и readiness.
3. **Транспорт и маршрут.** Connection refused обычно означает отказ на пути/порту, timeout требует проверки потерь/фильтрации/маршрута; ни один из них сам по себе не доказывает конкретную причину. Проследи src → CNI/узел → реализация Service → backend. Учитывай ingress и egress NetworkPolicy, DNS egress, маршруты, NAT, MTU/MSS и conntrack только по относящимся к ним признакам. Не угадывай CNI, kube-proxy/iptables/IPVS/eBPF. Успех ping/ICMP не подтверждает TCP, а неуспех ping не доказывает недоступность приложения.
4. **TLS и HTTP.** Различай CA/SAN/срок сертификата/SNI, протокол TLS, HTTP 401, 403, 404, 502 и 504. Учти Host/path, Ingress/Gateway, reverse proxy и backend port. TCP connect не доказывает успешный TLS или HTTP. Не советуй отключить проверку сертификатов либо ослабить авторизацию.

Дай до трёх наиболее различающих read-only проверок, с исходной точкой и ожидаемым наблюдением. Разрешённые инструменты чтения используй для получения фактов; shell и изменения не запускай. Если нужна ручная проверка из Pod, явно назови её ручной, используй существующий одобренный диагностический контейнер и не предлагай автоматически создавать privileged/debug Pod, устанавливать пакеты или менять политики.

Диагностическая проверка не включает «временно добавьте правило»: это изменение конфигурации, даже если рядом приведён kubectl get. Имя Service DNS, наличие cert-manager и namespace контроллера устанавливай по фактам, а не по типичному примеру. Без цели предложи сначала обнаружение объектов; допускается ответ без команды.

Для HTTP/SSE статус 200 подтверждает заголовки, но не завершение тела. ERR_INCOMPLETE_CHUNKED_ENCODING и upstream prematurely closed connection указывают на неполный транспорт, а не сами по себе на лимит токенов или OOM модели. Различай общий deadline и таймаут между чтениями: proxy_read_timeout не является общей длительностью запроса. Проверяй фактический прокси/сервис, request ID, длительность и терминальное событие SSE; имена контейнера и Compose-сервиса могут различаться. Не подставляй выдуманные параметры timeout из других продуктов.
