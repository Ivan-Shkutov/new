# Kubernetes: правила диагностики

- Сначала разбери status.reason/status.message именно выбранного объекта, условия, события его UID и состояние владельца. Узел бери из spec.nodeName. Не используй новый Pod с другим UID как доказательство о старом.
- Running не равен Ready. Completed/Succeeded с успешными exit codes может быть нормальным завершением Job. Старый Failed/Evicted Pod не доказывает текущий отказ приложения: проверь доступную замену и endpoints.
- Exit code 137 обычно соответствует SIGKILL; сам по себе он не подтверждает и не исключает OOMKilled. Нужны reason/lastState, события и данные памяти нужного времени. OOMKilled и Evicted различаются; HPA не выселяет Pod.
- Если status.message прямо сообщает превышение EmptyDir sizeLimit, назови точный том и лимит. Это причина выселения. Причина роста файлов требует отдельных данных. Не выдумывай путь тома; EmptyDir, root filesystem и PVC — разные хранилища.
- Текущий Ready, свободная память или диск кластера не исключают прошлого давления на конкретном узле. Для такого вывода нужны данные фактического узла за время инцидента.
- Requests/limits и резервирование — не фактическая утилизация. CPU, память, root filesystem узла и PVC не подменяют друг друга. Недоступные метрики не равны нулю.
- Счётчики resources.pods.count/phases/healthy/unhealthy вычислены Pulse, а items — ограниченная выборка с проблемными объектами в начале. Не считай items полным списком и не отрицай наличие Pods при ненулевых счётчиках. truncated означает неполноту.
- Уровень info, текст SendText или отсутствие слова error не доказывают успешную доставку, исправность всего сервиса или отсутствие других ошибок. Для штатной записи не придумывай причины аварии.
- Учитывай известную версию Kubernetes, API и сетевого плагина. Если версия/реализация неизвестна, опиши условную проверку вместо уверенного предположения. Не читай Secrets для диагностики.
