# Pulse 0.7.0: новый Обзор D+B и обновление с 0.6.1

Вкладка Обзор получила три круга утилизации (CPU, RAM, диски), историю за 1/6/24 часа, семь карточек workloads, карту кластеров и блок «Требует проверки» с переходом к ресурсу/анализу. Все показатели приходят из источников; демонстрационные значения в приложение не встроены.

[Скриншот браузерной проверки на подписанных тестовых данных](images/overview-070-test.png).

## Значения кругов

- CPU: non-idle time узлов, взвешенный по CPU; включает iowait. node_exporter `node_cpu_seconds_total`.
- RAM: `100 × (1 − sum(MemAvailable)/sum(MemTotal))`; ёмкость учитывается весом, а не средним арифметическим процентов узлов.
- Диски: `100 × (1 − sum(filesystem_avail)/sum(filesystem_size))` для корневой файловой системы `/` узлов. Это занятое/недоступное обычному пользователю место (включая резерв), а не определение физических HDD/SSD и не PVC. Дополнительные mountpoints в этот круг не входят.
- Повторные scrape jobs уменьшаются через max по instance/cpu/mode. Настройте уникальные и согласованные instance/cluster labels. Неполное покрытие exporter ограничивает точность агрегата; круг не подтверждает наличие метрик всех узлов.
- Нужны Prometheus/VictoriaMetrics и node_exporter. Без источника/серий — нейтральный круг «—» и «нет данных». История ограничена примерно 120 точками и кешируется на 30 секунд. Пропуски графика не соединяются.
- При выборе нескольких кластеров утилизация не усредняется: выберите один кластер слева. Workloads суммируются по доступным снимкам с отметкой неполноты.

## Семь карточек, как в примере

DaemonSets, Deployments, ReplicaSets и StatefulSets показывают долю объектов, у которых ready replicas достигли желаемого числа и observedGeneration актуален при наличии generation. Это показатель готовности, а не доказательство завершённого rollout. Scaled-to-zero выделяется отдельно.

Pods: phase Running и condition Ready=True. Jobs: condition Complete=True. CronJobs: расписание не приостановлено (не означает, что последнее задание завершилось успешно). Доля включённых CronJobs подписана «Включены». Для нулевого количества нет фиктивных 100%. Ошибки, неполные выборки и устаревание показаны отдельно.

## Скачать обновление

В авторизованном браузере GitHub скачайте из `releases` архив `pulse-clusters-0.7.0-complete.tar.gz` и `.sha256` через Download raw file. На компьютере Windows:

```powershell
scp "$env:USERPROFILE\Downloads\pulse-clusters-0.7.0-complete.tar.gz" dito@10.129.160.10:/home/dito/
scp "$env:USERPROFILE\Downloads\pulse-clusters-0.7.0-complete.tar.gz.sha256" dito@10.129.160.10:/home/dito/
```

На сервере сначала проверить архив (рабочее приложение продолжает работать):

```bash
cd /home/dito
sha256sum -c pulse-clusters-0.7.0-complete.tar.gz.sha256
tar --keep-old-files -xzf pulse-clusters-0.7.0-complete.tar.gz -C /opt
cd /opt/pulse-clusters-0.7.0
sha256sum -c MANIFEST.sha256
```

Если любая команда неуспешна — остановитесь. Для нового каталога не используйте имя уже существующей установки.

## Сохранить PeopleHub, qwen, документы и историю

От root на вашем сервере:

```bash
cd /opt/pulse-clusters-0.6.1
./pulse backup --output-dir /root/pulse-backups-before-070
```

Backup кратко останавливает Pulse и возвращает его обратно. vLLM остаётся работать. В выводе будет полный путь к созданному архиву. Сохраните его: файл содержит credentials, его нельзя отправлять в чат/GitHub.

Только после успешного backup остановите прежнюю панель:

```bash
cd /opt/pulse-clusters-0.6.1
./pulse stop
```

В новой установке создайте runtime и восстановите **конкретный только что созданный backup**, заменив путь в команде:

```bash
cd /opt/pulse-clusters-0.7.0
./pulse init --port 8090
./pulse restore /root/pulse-backups-before-070/ИМЯ-СОЗДАННОГО-АРХИВА.tar.gz --confirm-restore
./pulse start
./pulse check
```

Не выполняйте restore с буквальным placeholder. Рядом с backup должен лежать его `.sha256`. Restore восстанавливает базу, пароль, registry.key и настройки. После запуска ожидается версия 0.7.0 и PeopleHub в overview. Не удаляйте старый каталог и backup до завершения приёмки. Не запускайте два процесса с одним runtime.

## Проверить и подключить метрики

1. Откройте панель через прежний SSH-туннель на 8090, обновите страницу. Внизу должна быть версия 0.7.0.
2. Выберите PeopleHub. Семь карточек должны содержать реальные количества из API. Сверьте `kubectl get ds,deploy,job,cronjob,rs,sts,pods -A` на административной машине.
3. Настройки → PeopleHub → Настроить: введите доступный с сервера URL Prometheus/VictoriaMetrics **до** `/api/v1/query`, авторизацию/CA при необходимости и режим shared с точными cluster labels либо dedicated для источника только одного кластера. Реальный адрес и labels пока пользователем не сообщены; они не угадываются.
4. В Обзоре проверьте круги и историю. Если серий нет, проверьте наличие node_exporter, названия labels, mountpoint `/` и успешность scrape. Доступ к Kubernetes API сам по себе не даёт CPU/RAM/HDD consumption.
5. Переключите 1/6/24 часа, проверьте время источника. Отсутствие данных должно оставаться видимым.
6. В «Требует проверки» нажмите «Почему?» у Pod. Гипотезу qwen сравните с фактами.

## Откат

Остановите новую установку, затем из старого каталога запустите `./pulse start-offline`. Старый runtime сохранён отдельно; записи, сделанные после перехода на 0.7.0, автоматически обратно не переносятся. Сохраняйте новые данные отдельным backup перед откатом.

93 pytest-теста прошли (включая scope API, статусные правила, пустые/неполные данные, scoped PromQL, NaN/пустые серии и историю). Docker-образ собран и запущен, check подтверждает 0.7.0. Браузер: прежний smoke и новый dashboard smoke — 7 карточек, 3 круга/графика, переключатель интервала, отсутствие метрик, mobile и отсутствие JS ошибок. Настоящие Prometheus/VictoriaMetrics пользователя ещё не подключены: запросы покрыты контролируемыми ответами, их совместимость в контуре требует проверки после указания URL/labels.
