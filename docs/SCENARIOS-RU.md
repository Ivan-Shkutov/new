# Диагностика по сценариям в Pulse 0.15.1

Откройте проблему в Обзоре кнопкой ✧ либо выберите Pod в Ресурсах и откройте диагностику. Слева выбирается один из шести сценариев, справа появляется один результат. Новый запуск заменяет результат; предыдущий ответ модели не становится доказательством следующего разбора.

| Сценарий | Что проверяет Pulse | Что читать в результате |
| --- | --- | --- |
| **Краткий разбор** | Выбранный Pod и UID, причина в status/events, владелец и готовность замены, связанные Service/Endpoints. Дополнительные чтения ограничены симптомом и бюджетом. | Что произошло, подтверждённая причина, важность и первая полезная проверка. |
| **Подробный разбор** | Расширенный набор связанных объектов, события, доступные логи, storage/probes, доступная история метрик и Astra. | Связь фактов, гипотезы и пробелы, которые мешают подтвердить диагноз. |
| **Причины сбоя** | Статус и события, релевантные логи, настройки Pod, состояние фактического узла и доступная история. | Подтверждённая причина отдельно от гипотез; чем проверить каждую гипотезу. |
| **Последствия сбоя** | Владелец, текущие реплики, связанные Service и адреса Endpoints. | Подтверждённое влияние и возможные последствия, для которых ещё нужны данные. |
| **План устранения** | Причина, конфигурация и владелец Pod, относящиеся к симптому storage/probes/логи. | Короткая последовательность действий, команды чтения, их назначение и ожидаемый результат. |
| **Проверка восстановления** | Повторное чтение состояния владельца, связанных Pod и Endpoints с проверкой связей UID и полноты ответа. | Восстановление подтверждено, не завершено либо не подтверждено доступными данными. |

Для Node, Deployment, StatefulSet, DaemonSet, ReplicaSet, Job, CronJob и PVC доступны свежие status/spec/events и связанные Pod с проверкой UID. Для CPU/RAM/disk сверяются свежесть и покрытие узлов Kubernetes. Полная цепочка проверки восстановления реализована для Pod и его владельца; для остальных объектов доступность приложения остаётся неподтверждённой. Отсутствие данных не считается нормальным состоянием. Бюджет сбора Pod: краткий и последствия — 35 с, подробный — 90 с, причины — 75 с, план — 70 с, восстановление — 45 с; для остальных ресурсов — 30 с. Генерация модели имеет отдельный timeout. Недоступный источник отмечается в журнале.

## Откуда берётся вывод

Pulse сам собирает факты через API. Подтверждённые поля результата строятся из этих фактов: модель не может своим текстом изменить UID, причину из `status.message` или объявить восстановление. В остальных сценариях модель добавляет ограниченные гипотезы и следующие проверки по строгому JSON-контракту. Нарушение контракта или неизвестная ссылка на доказательство приводит к результату Pulse с отметкой об ошибке модели.

Например, `Evicted` и сообщение `Usage of EmptyDir volume "data" exceeds the limit "1Gi"` подтверждают превышение лимита этого временного тома. Они сами по себе не доказывают заполнение корневого диска узла, причину роста данных или недоступность всего приложения. Для этих выводов нужны отдельные наблюдения.

Раздел источников свёрнут по умолчанию. Раскройте его, чтобы посмотреть выполненные проверки, ссылки `E##`, недоступные источники и ошибки движка. Там же блок «Правила и инструменты» показывает применённые rules/skills и вызовы Holmes. Команды `kubectl` служат для воспроизведения чтений оператором. Pulse не запускает shell и не выполняет исправления в кластере.

## Движок и настройки

В диагностике явно выберите **«Локальная LLM»** либо настройки кластера. Во втором случае используется включённый для этого кластера провайдер: Astra AI или HolmesGPT, иначе локальная модель. При ошибке скрытого переключения на другой движок нет.

- Для локальной модели проверьте сохранённые URL, model alias и ключ в настройках Pulse. Адрес должен быть доступен из процесса или контейнера Pulse. `127.0.0.1` подходит только при соответствующей сетевой схеме.
- Для Astra AI задаётся полный URL `chat/completions`, model ID и действующий Bearer token. Проверка потока должна завершиться успешно. HTTP 403 означает отказ доступа к endpoint; обновление интерфейса не выдаёт права учётной записи.
- Для HolmesGPT сначала подготовьте отдельную конфигурацию, запустите сервис, выполните проверки ответа и фактического вызова разрешённых инструментов, затем включите его для кластера. Подробности и ограничения проверки реального образа описаны в [HOLMES-RU.md](HOLMES-RU.md). Путь к runtime берите из действующего контейнера, а не из примера старой версии.

**«Проверка восстановления» не требует LLM.** Вердикт строится по свежим измерениям. Готовые реплики и Endpoints подтверждают только проверенную часть цепочки; они не заменяют внешний запрос через Ingress, DNS, балансировщик и клиентскую сеть. Если исходный Pod удалён из API и обновлённого снимка, Pulse может взять проверенную связь с владельцем из журнала текущей сессии. Предыдущий текст модели не используется. Владельца, заменяющие Pod и endpoints всё равно нужно прочитать заново; старое наблюдение само по себе не подтверждает восстановление.

Логи Kubernetes и Astra Monitoring — отдельные источники. Работающий Astra AI не доказывает доступность поиска логов. Нужны правильные поля cluster/namespace/Pod, API-контракт, токен и доступ к источнику.

## Короткая приёмка на вашем сервере

1. После обновления выполните `./pulse check` и `./pulse doctor --cluster peoplehub`, обновите страницу с Ctrl+F5.
2. Откройте известную проблему. Сверьте cluster, namespace, имя и UID с `kubectl`; не создавайте новую аварию ради проверки.
3. Запустите каждый сценарий. В кратком результате должны быть конкретные факты выбранного объекта, а не общий журнал всех запросов. Проверьте ссылки на источники.
4. Для известного `EmptyDir`-инцидента убедитесь, что причиной указано превышение лимита тома, а заполнение диска узла не объявлено доказанным без отдельного источника.
5. Откройте другой Pod: предыдущий результат не должен переноситься. Быстро смените сценарий: поздний ответ старого запуска не должен заменить новый.
6. Запустите проверку восстановления. Если данные неполные, UID изменился без подтверждённой связи или источник недоступен, результат должен сообщать об ограничении.

Автотесты и контролируемые API-стенды проверяют программный контракт. Качество вашей модели, реальные права Kubernetes/Astra, доступность Holmes и сеть подтверждаются этой приёмкой на сервере. Дополнительная команда `./pulse llm-check --show-answers` проверяет сохранённую локальную модель на учебных примерах; это отдельная проверка модели, а не замена приёмки новых шести сценариев.

Если во время проверки меняются настройки источников или локальной модели, откройте диагностику заново: результат прежнего подключения не считается актуальным. Смена кнопки удаляет прежнюю активную сессию; уже начатый внешний запрос может продолжаться до timeout, но его поздний ответ не заменит новый результат.
