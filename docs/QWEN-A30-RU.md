# Qwen3.8-27B и две A30: подтверждённое состояние

Обновлено 5 ноября 2026 по данным владельца сервера. Это контекст настройки,
а не автоматическое обнаружение или измерение из облачной среды разработки.

## Рабочая конфигурация

- p0-app5000: две NVIDIA A30 по 24 576 MiB, всего 48 ГиБ.
- Контейнер vllm-qwen, образ vllm/vllm-openai:v0.30.0-ubuntu2404.
- API: http://127.0.0.1:8002/v1, served alias qwen, путь /models/qwen3.8.
- Локальная README указывает base_model Qwen/Qwen3.8-27B, сборку W4A16/AWQ g128.
- config.json: qwen3_5 / Qwen3_5ForConditionalGeneration, hidden_size=5120, 64 слоя.
- compressed-tensors, pack-quantized, статические INT4 веса, группы по 128; два файла весов 18,21 ГиБ.
- Подтверждённые аргументы: gpu-memory-utilization 0.85, max-model-len 131072,
  max-num-seqs 4, reasoning-parser qwen3. Параметр tensor-parallel-size отдельно не прислан.
- В момент измерения около 20 147 MiB занято на каждой карте. Это веса, кэш и буферы,
  а не измерение одного размера весов. В том выводе OOMKilled=false, RestartCount=0.

Версия архитектуры qwen3_5 не опровергает указанную базовую модель Qwen3.8.
Название каталога само по себе её не подтверждало: основание — предоставленная карточка.
Исходные веса и их хеши с официальным checkpoint независимо не сопоставлялись.
Сохранённые vision и MTP указаны автором квантования; наличие MTP-файла не доказывает,
что speculative decoding включен в текущем vLLM.

Pulse подключается к имеющейся модели. Этот выпуск не запускает ещё одну LLM,
не меняет веса, GPU-параметры, Astra или конфигурацию vLLM. Выбор движка явно
сохраняется в Pulse; для прямой локальной генерации используйте «Локальная LLM напрямую».

## Результат пользовательского учебного прогона

6 из 6 ответов завершены с finish_reason=stop. Среднее время 5,348 с,
медиана 4,998 с, диапазон 4,107–7,113 с. API сообщил reasoning_tokens=0 для всех
ответов. Это не сравнение с другой моделью и не проверка длинного reasoning.
Входы короткие, 284–348 prompt tokens; скорость больших расследований не измерена.

Причины EmptyDir, selector Service, DNS egress и TLS распознаны в основном правильно.
Инструкция внутри лога не была выполнена, SendText не был принят за доказательство доставки.
Выявлены ошибки: OOM приравнен к превышению cgroup-лимита, Ready — к памяти в пределах
лимита, namespace/name использован как имя Pod, kubectl top предложен для истории,
придуманы Deployment/labels/cert-manager, а временная правка политики названа проверкой.

В 0.15.1 эти случаи вошли в правила и учебную проверку `./pulse llm-check`.
Основные сценарии получают строгий JSON только для гипотез/проверок; команды
строит Pulse из полученных объектов. Известные советы изменить инфраструктуру
словами отклоняются. Это консервативный фильтр, а не полная семантическая проверка
естественного языка: гипотезы всё равно необходимо сверять с доказательствами.

## Следующая приёмка

1. Обновите Pulse с тем же runtime и убедитесь в версии/build через `./pulse check`.
2. Проверьте известный Pod каждым из шести сценариев. Результат заменяется; история
   прежних ответов не подмешивается. Источники раскрываются отдельно.
3. Выполните `./pulse --runtime ПУТЬ llm-check --show-answers` из действующего релиза.
   Девять вопросов учебные, кластер не меняют. JSON-отчёт сохраняется в runtime.
4. Оцените ответы по review: завершение генерации не означает правильности причин.
5. Для новой модели или режима reasoning используйте одинаковые входы, бюджет,
   контекст, нагрузку и несколько повторений. Улучшение процентов не заявляется без A/B.

Увеличивать параметры модели для устранения прежнего 10-секундного обрыва не требуется:
он был локализован в цепочке Astra. Изменение лимита контекста само по себе не является
настройкой максимальной длины ответа. max-model-len учитывает вход и генерацию вместе.

## Astra: отдельно от Pulse

У пользователя Astra 1.6.0 на v0-inf0090 проксировала AI-запрос через admin-ui/nginx,
gatekeeper и admin-backend к vLLM на p0-app5000:8002. Gatekeeper закрывал запрос через
10,0107 с, nginx фиксировал upstream prematurely closed connection. Установлен
поддерживаемый параметр --server-write-timeout=300s в Compose-сервисе gatekeeper-idp
(имя контейнера gatekeeper). После правки пользователь подтвердил работу Astra.

Этот выпуск не редактирует /opt/am/astra-monitoring/docker-compose.yml.
HTTP 200 без завершения SSE не доказывает готовый ответ, а 403 — отдельная ошибка доступа.
Работающий Astra AI не подтверждает подключение поиска логов Astra к Pulse.
Реальный контракт filter_preview по-прежнему не проверен; адаптер логов не выдаётся за
подтверждённо работающий только на основании успеха модели.

В предоставленных ранее debug-логах Gatekeeper был Authorization. Не переносите
такой журнал в Pulse, GitHub или чат без редактирования секретов.
