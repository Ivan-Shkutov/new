# Pulse Dark 0.8.0: понять состояние кластера с первого взгляда

Выбран пользователем вариант 1. Развитие рабочего обзора D+B: готовность, причины проблем и свежесть данных на первом экране.

- [Здоровый кластер: 6/6 зелёным](images/health-080/healthy.png).
- [Отказ узла: 5/6 красным и CrashLoopBackOff](images/health-080/critical.png).

Изображения сняты с приложения в Chromium на явно подписанных тестовых данных. Это не измерения инфраструктуры пользователя.

## Что видно сразу

1. **Состояние Kubernetes.** Сводка по наблюдаемым объектам: готово / критические сигналы / предупреждения / неизвестно / устарело / пауза. Критические причины и имена объектов показаны сразу под заголовком.
2. **Узлы Ready.** 6/6 зелёным при свежей полной выборке и подтверждённой готовности; 5/6 красным. DiskPressure/MemoryPressure/PIDPressure/NetworkUnavailable тоже могут сделать карточку красной даже при 6/6 Ready.
3. **Активные Pods Ready.** Завершённые и удаляемые Pod исключены из знаменателя. Общее число объектов остаётся в карте кластеров и workload-карточке.
4. **Критические сигналы.** Считаются симптомы объектов, не уникальные аварии: сбой Pod и его контроллера могут иметь одну причину. Кнопка ведёт к приоритетному списку.
5. **CPU/RAM/диски.** Круги и графики 1/6/24 часа. Ниже 75% — обычный цвет, 75–90% — предупреждение, от 90% — красный. Это ориентиры утилизации, а не гарантия аварии. Без метрик/при ошибке показаны «нет данных».
6. **Семь workloads.** Цвет зависит от состояния, а не только от процента. Jobs 1/2 completed с одним выполняющимся заданием не считаются аварией. Приостановленный CronJob и scaled-to-zero не объявляются сломанными автоматически.
7. **Узлы подробно.** Разворачиваемая таблица: Ready, причины, Cordon, размещённые активные Pods, IP, версия. «Подробнее» в карточке узлов раскрывает таблицу.
8. **Проблемы.** Приоритет critical → warning, фильтр, понятная причина, объект/namespace и переход «Почему?» для Pod либо к ресурсу.
9. **Warning-события.** Отдельный сворачиваемый контекст за 15 минут; старое событие не превращает здоровый кластер в красный.
10. **Автообновление.** Обзор обновляется раз в 30 секунд, кроме скрытой вкладки, открытого диалога или выбора в select. Серверный polling выполняется независимо. Фильтр проблем сохраняется при обновлении.

## Правила оценки

- Узел Ready=False/Unknown и Pressure=True — критический сигнал. Отсутствие condition Ready — неизвестное состояние, а не подтверждённая исправность.
- CrashLoopBackOff, ImagePullBackOff, ErrImagePull, CreateContainerConfigError, CreateContainerError, InvalidImageName, RunContainerError у текущего неготового контейнера — critical.
- Pending меньше 5 минут — warning; от 5 минут — critical. Running без Ready меньше 3 минут — warning; от 3 минут — critical. При неизвестной длительности — warning, без выдуманного возраста.
- Неготовый контроллер/rollout — warning. ProgressDeadlineExceeded либо Available=False дольше 5 минут — critical. Готовность реплик не является отдельной гарантией полного завершения rollout.
- PVC Lost — critical, Pending — warning. Failed Job/Failed Pod — warning с напоминанием проверить актуальность сохранённого объекта.
- Рестарты — сумма счётчиков текущих объектов, не частота за последние минуты. Сам по себе большой накопленный счётчик не делает кластер красным.
- Снимок старше max(120 секунд, 3×poll interval), пауза, недоступные типы, усечённая выборка и отсутствующие сведения не получают общий зелёный статус. Ранее наблюдавшиеся проблемы помечаются как данные прошлого снимка.
- Если в неполном, но свежем снимке есть конкретная критическая проблема, она остаётся красной вместе с предупреждением о неполноте.

Оценка относится к доступным Kubernetes-наблюдениям. HTTP health процесса, состояние Kubernetes, реальное покрытие exporters и качество ответа LLM — разные проверки. Нагрузка внешних бизнес-зависимостей/сетевые SLO не определяются автоматически без источников.

## Метрики

Используется ранее добавленный Prometheus/VictoriaMetrics источник. При shared обязательны точные cluster labels; dedicated допустим для выделенного хранилища. node_exporter нужен для utilisation узлов. Дисковый круг — корневые файловые системы `/`, не все физические HDD/SSD и не PVC. Отсутствующие серии остаются неизвестными. Пропуски истории не соединяются.

## Скачать выпуск

В авторизованном браузере GitHub скачайте из `releases` через Download raw file:

- `pulse-clusters-0.8.0-complete.tar.gz`;
- `pulse-clusters-0.8.0-complete.tar.gz.sha256`.

Windows PowerShell на вашем компьютере:

```powershell
scp "$env:USERPROFILE\Downloads\pulse-clusters-0.8.0-complete.tar.gz" dito@10.129.160.10:/home/dito/
scp "$env:USERPROFILE\Downloads\pulse-clusters-0.8.0-complete.tar.gz.sha256" dito@10.129.160.10:/home/dito/
```

На сервере от root:

```bash
cd /home/dito
sha256sum -c pulse-clusters-0.8.0-complete.tar.gz.sha256
tar --keep-old-files -xzf pulse-clusters-0.8.0-complete.tar.gz -C /opt
cd /opt/pulse-clusters-0.8.0
sha256sum -c MANIFEST.sha256
```

При ошибке остановитесь. Не распаковывайте поверх старого каталога или runtime.

## Обновить с сохранением PeopleHub, qwen и истории

Выполните backup из **каталога действующей версии**. Ниже приведён путь исходной установки 0.6.1; если вы уже установили 0.7.0, используйте `/opt/pulse-clusters-0.7.0` в первом cd.

```bash
cd /opt/pulse-clusters-0.6.1
./pulse backup --output-dir /root/pulse-backups-before-080
```

Backup содержит пароль и registry.key; его нельзя отправлять в чат/GitHub. После успешного backup сохраните полный путь созданного архива и остановите старую панель из того же каталога:

```bash
./pulse stop
```

В новой установке:

```bash
cd /opt/pulse-clusters-0.8.0
./pulse init --port 8090
./pulse restore /root/pulse-backups-before-080/ИМЯ-СОЗДАННОГО-АРХИВА.tar.gz --confirm-restore
./pulse start
./pulse check
```

Замените placeholder конкретным путём из вывода backup. Ожидается 0.8.0. Формат SQLite/подключений совместим с 0.6.1/0.7.0. Восстанавливаются пароль, ключ, подключения, настройки модели, документы и история. vLLM продолжает работать отдельно. Старый runtime остаётся на месте.

Через прежний туннель откройте браузер, обновите страницу, выберите PeopleHub. Сравните Nodes Ready с `kubectl get nodes`; Pods с `kubectl get pods -A` с учётом завершённых и удаляемых. Проверку аварий не выполняйте созданием отказа в production. На вашем сервере и кластерах выпуск удалённо не применялся.

Токен reader может истечь независимо от обновления Pulse. При 401 экспортируйте новый reader kubeconfig и обновите подключение, не заменяя его административным.

## Откат

В новом каталоге `./pulse stop`, затем в каталоге прежней версии `./pulse start-offline`. Старый runtime сохранён отдельно. Новые записи обратно не переносятся автоматически; перед откатом сохраните backup новой установки.

## Доказательства проверок

- Pytest: 123 теста (включая 30 проверок health) при Python 3.12, Linux amd64. Один deprecation warning тестового клиента Starlette/httpx.
- Настоящая Docker-сборка и старт, `/healthz` и защищённый overview.
- Основной браузерный smoke: навигация, настройки, документы/поиск/удаление, desktop/mobile.
- Dashboard smoke: 3 круга/графика, 7 workloads, интервалы и отсутствие метрик.
- Health browser regression: 6/6 зелёный → 5/6 красный, имя отказавшего узла, critical filter, CrashLoop → корректный Pod в форме расследования, работающий Job без ложной аварии, устаревший снимок без зелёного статуса, mobile без переполнения и JS ошибок.

Реальные API источников пользователя требуют приёмки после обновления. Прохождение тестов не означает отсутствия всех возможных дефектов или замену мониторинга бизнес-сервисов.
