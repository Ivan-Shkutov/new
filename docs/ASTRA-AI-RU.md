# Как изучить и подключить ИИ Astra Monitoring

Два присланных текстовых файла содержат одинаковый пример `cox filter create error: sn is empty` и ответы меню. Они показывают формулировки задач (краткий/расширенный анализ, причины, последствия), но не доказывают, что ИИ выполнял Kubernetes-команды или читал соседние логи. Расшифровка `sn`, HTTP 500/502 и отсутствие влияния на остальные запросы в этих ответах — гипотезы. В примере нет серверной трассировки, которая подтверждала бы их.

Адрес `http://10.128.77.23/infrastructure/map` — веб-интерфейс. Он не определяет контракт API ИИ. В текущей облачной среде нет доступа к этой частной сети; запросы из вашей авторизованной браузерной сессии здесь не наблюдались.

## Исследовать фактический запрос

1. Откройте Astra своим обычным аккаунтом. F12 → Network → Fetch/XHR, включите Preserve log, очистите список. Выберите одну строку лога.
2. Нажмите «Сжатый анализ». Найдите новый запрос. Запишите относительный путь, HTTP-метод, Content-Type, JSON Request Payload и структуру Response. Если ответ потоковый, откройте EventStream и запишите типы событий, поле текста и сигнал завершения.
3. По тому же логу нажмите «Расширенный анализ», затем задайте обычный вопрос. Сравните запросы: изменяется только текст вопроса или также mode, context, conversation_id, log IDs, диапазон времени, список инструментов? Выполняются ли дополнительные запросы к логам до/после ответа? Наличие чата само по себе не доказывает tool calling.
4. Запишите версию Astra и найдите документацию через её интерфейс/поддержку. Не угадывайте URL Swagger и не сканируйте произвольные endpoints. Уточните поддерживаемую сервисную авторизацию и права на API анализа.

Обезличенный шаблон для передачи:

```text
Версия Astra:
Метод и путь ИИ:
Content-Type запроса:
Тип авторизации (только название, без значения):
JSON запроса с заменёнными внутренними данными:
JSON ответа или имена SSE-событий:
Как передаётся исходный лог / log_id / временной диапазон:
Как продолжается разговор:
Отличия brief / extended / обычного вопроса:
Документация и лимиты API:
```

Не присылайте Authorization, cookies, API keys, полный HAR или Copy as cURL из рабочей сессии: они могут включать credentials и внутренние данные. JSON можно заменить структурным примером с теми же ключами.

## Варианты интеграции

- Использовать официальный API ИИ Astra из backend Pulse. Кнопка ✧ направляется к этому провайдеру с контекстом/историей по его реальному контракту, сервисный credential сохраняется зашифрованно. Для SSE нужен разбор именно его формата. Пользовательские cookies не копируются в сервер.
- Использовать qwen/Holmes, передавать им реальные логи Astra, события, status.message, узел, владельца и метрики. Аналогичное меню не означает одинаковую модель или качество ответа: результат проверяется на известных случаях.

В Pulse 0.10.0 реализован второй путь через существующий адаптер логов Astra и журнал доказательств. Совместимость адаптера с вашей версией нужно подтвердить. **Кнопка ещё не перенаправлена на собственный ИИ Astra:** точный endpoint, payload, streaming и сервисная авторизация не предоставлены. Одинаковые ответы или пересказ возможностей не заменяют контракт. Новый неизвестный адрес `/api/.../ai` не выдумывается.

## Почему не выполнять PUT из ответа ИИ

`PUT /api/v1/states/...` изменяет состояние. Это не проверка доступности и не доказательство причины HTTP 500. Ответ на пустое тело или без авторизации может быть совсем другой ошибкой. Не повторяйте такой запрос в production ради диагностики.

Если исходный лог действительно содержит HTTP 500 и `cannot set state`, сначала сопоставьте время/agent_id/request_id с серверными логами процесса на порту 8427 и его зависимостями. HTTP 500 не доказывает корректность входного payload агента: сервер мог некорректно обработать именно эти данные. Конкретный путь логов, причина отказа БД и необходимость restart/reboot без этих данных неизвестны. В предоставленных текстовых файлах исходной HTTP-трассы этого запроса нет.
