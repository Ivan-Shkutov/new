# Локальная LLM Pulse 0.15.0: настройка и проверка ответов

## Подключение

В Настройках → «Локальная модель» сохраните URL и Model ID. Для ранее работавшего vLLM на p0-app5000 использовались `http://127.0.0.1:8002/v1` и `qwen`. Ранее ключ не требовался; текущую доступность надо проверить. `qwen` — served model ID, не доказательство конкретных весов/размера/квантизации.

На сервере можно проверить каталог моделей:

```bash
curl --fail --silent --show-error http://127.0.0.1:8002/v1/models
```

Наличие модели в каталоге не доказывает генерацию. Введите ключ в защищённое поле Pulse, если ваш vLLM требует его, и нажмите «Проверить ответ». Это проверка завершённого ответа API, а не качества диагноза.

Для анализа по ✧ выберите **«Локальная LLM напрямую»** на странице «Диагностика». Чтобы локальная модель использовалась как движок Peoplehub по умолчанию, в настройках кластера выключите «Использовать ИИ Astra» и Holmes, затем сохраните. Для общего чата выберите «Локальная LLM — напрямую». Astra logs и Prometheus — независимые источники: их настройки не определяют провайдера ответа.

Не запускайте вторую vLLM и не перезапускайте рабочую модель без конкретной причины. Host network Pulse позволяет обращаться к vLLM на loopback этого же сервера.

## Какие правила реально получает модель

Pulse читает эти файлы и включает их в `messages[0].content` при каждом новом запросе, в общем чате и в анализе проблем:

- [BASE.md](../pulse_app/ai_rules/BASE.md): роль Senior DevOps/SRE, уровень экспертизы инженера с опытом более 10 лет, краткость, доказательства и действия. Это стандарт ответа, а не утверждение о личном стаже модели.
- [KUBERNETES.md](../pulse_app/ai_rules/KUBERNETES.md): UID/время/состояние объектов, Ready/Completed, Evicted/EmptyDir/OOM, метрики и полнота данных.
- [NETWORK.md](../pulse_app/ai_rules/NETWORK.md): DNS → Service/endpoints → TCP/маршрут/CNI/политики → TLS/HTTP. Добавляется при сетевом или TLS/API-вопросе.

Также выбираются до трёх тематических сценариев плюс общий из 12 встроенных в `pulse_app/runbooks.py`. Выбор учитывает реальную reason/message и вопрос оператора. Имена ключей nodeName и общие примечания о Ready/Pressure больше не выбирают сценарий сами по себе. Конкретный наблюдаемый симптом сохраняет приоритет.

В источниках → «Правила и инструменты» видны `policy:senior-devops · applied` и выбранные `skill:*` с версиями. Build ID включает Markdown правил; смена файла меняет идентичность сборки. После изменения правил приложение нужно пересобрать и перезапустить. Веса vLLM и его конфигурация этим не меняются; копировать правила в каждый диалог вручную не требуется.

## Как выглядит ответ

Основной интерфейс использует [шесть фиксированных сценариев](SCENARIOS-RU.md). «Краткий разбор» — вывод и четыре строки: причина, влияние, техническая важность, первый шаг. Основная таблица ограничена 120 словами. Подробный разбор и причины добавляют до трёх явно помеченных гипотез и следующую проверку; последствия отделяют подтверждённое влияние от рисков; план содержит конкретные команды чтения и условные рекомендации.

Модель возвращает только JSON по схеме из [workflows.py](../pulse_app/workflows.py): `hypotheses` и `checks`, оба массива обязательны, до трёх элементов. Pulse проверяет структуру, размер и ссылки `E##`. Формат и ссылки можно проверить автоматически; смысл гипотез требует сверки с доказательствами. Для краткого сценария дополнение модели ограничено 80 словами, для остальных — 300. Сырой JSON и незавершённые черновики не появляются в основном результате.

Подтверждённая причина, факты, техническая важность и команды строятся программно. Например, EmptyDir `data` / `1Gi` не превращается в утверждение о заполнении всего узла. OOMKilled, CrashLoopBackOff, ImagePull и события scheduling/probe различаются. Высокая техническая важность возможна при подтверждённом отсутствии готовых адресов; бизнес-влияние без проверки приложения неизвестно. «Проверка восстановления» использует свежие данные Kubernetes и не вызывает модель.

Каждое нажатие — новая проверка без прежнего текста модели. Результат заменяется, источники остаются свёрнутыми. При ошибке модели показываются факты Pulse и отметка о недоступном дополнении. При смене подключения во время проверки результат не выдаётся за актуальный: откройте диагностику заново.

Совместимый API общего чата сохранён для старых клиентов и команды `llm-check`; это отдельный режим с временной историей. В основной навигации его заменили сценарии.

## Проверить настоящую локальную модель

После обновления выполняйте из каталога действующего выпуска, используя runtime активного контейнера:

```bash
pulse_runtime="$(docker inspect pulse-clusters-8090-pulse-1 --format '{{range .Mounts}}{{if eq .Destination "/runtime"}}{{.Source}}{{end}}{{end}}')"
./pulse --runtime "$pulse_runtime" check
./pulse --runtime "$pulse_runtime" llm-check --show-answers
```

Команда создаёт четыре временных диалога через Pulse, явно выбирает локальную модель, передаёт общие правила и удаляет сессии. Вопросы учебные: ClusterIP/Pod IP, EmptyDir, код 137 и TCP timeout после успешного DNS. Реальный Kubernetes этой командой не проверяется и не меняется. Каждый ответ может занимать до нескольких минут; время зависит от модели и нагрузки.

Отчёт записывается в **`<runtime>/llm-check-report.json`**. В нём реальные ответы вашей модели, число слов, время, передача правил и критерии `review` для ручной оценки. `generation_ok=true` означает завершённую генерацию и подтверждённую передачу профиля. `quality_verified=false` оставлен намеренно: автоматические проверки по ключевым словам не доказывают правильность ответа.

Для одного сценария:

```bash
./pulse --runtime "$pulse_runtime" llm-check --case network --show-answers
```

Приёмка: ответы короткие; нет выдуманных проверок; 137 не объявлен доказательством/исключением OOM; EmptyDir `data/1Gi` назван точно; timeout локализуется по исходному Pod, порту, endpoints и политике без предположения о CNI. Затем проверьте один реальный известный инцидент с UID, источниками и текущей готовностью замены. Результат «Проверить ответ» сам по себе эту приёмку не заменяет.

## Рекомендации к vLLM и знаниям

- Используйте подходящую Instruct-модель и её официальный chat template. Размер, квантизацию, VRAM/RAM и скорость выбирайте по ресурсам своего сервера и результатам этих вопросов; alias `qwen` не определяет качество.
- Нативный запрос Pulse использует `temperature=0.1`, `max_tokens=6000`, `stream=false`, timeout до 180 секунд. Это верхний предел генерации, а не просьба писать 6000 токенов. Краткость задают правила. Без проверки не уменьшайте лимит: thinking-модель может израсходовать его до финального ответа.
- Pulse отделяет один явный ведущий блок `<think>...</think>` от финального текста и не показывает `reasoning_content` как ответ. Незакрытый thinking-блок/ответ без content не считается успешным. Это не переключает режим модели: non-thinking следует включать на сервере только способом, документированным для конкретных весов/template. Неизвестные Qwen-specific параметры вслепую в запрос не добавляются.
- При обрыве/`finish_reason=length` ответ отмечается незавершённым. Проверьте загрузку vLLM, фактический template, token budget и время генерации; неправильную первопричину нельзя исправить одним увеличением timeout.
- Qdrant/embeddings полезны для поиска официальной документации нужной версии; они не обязательны для первого ответа и не заменяют доступ к Kubernetes/логам. Используйте [порядок импорта и проверки знаний](AI-KNOWLEDGE-RU.md).

Из среды разработки приватный vLLM пользователя не проверен. Локальные тесты подтверждают передачу правил, HTTP-контракт, фильтрацию служебных блоков и интерфейс на тестовых источниках. Качество реальных ответов подтверждается запуском `llm-check` на p0-app5000 и сверкой с данными своего инцидента.
