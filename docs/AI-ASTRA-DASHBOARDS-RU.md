# Проверка ИИ, логов Astra и дашбордов Pulse

## Три разных подключения

| Подключение | Что делает | Как подтвердить |
| --- | --- | --- |
| Kubernetes + Prometheus | Состояние объектов, CPU/RAM/root filesystem, история метрик | `./pulse doctor --cluster peoplehub`, детали кружков CPU/RAM/дисков |
| Astra logs | Получает журналы именно выбранных cluster/namespace/pod и времени | Успешный E16 с соответствующими записями и проверенным scope; не только HTTP 200 |
| Astra AI | Генерирует ответ по переданному контексту | «Проверить ИИ»/«Проверить поток Astra AI», затем контрольная ошибка с доказательствами |

403 от Astra AI не означает отказ Kubernetes или Prometheus. Недоступный E16 не доказывает, что логи прочитаны через AI endpoint. Статус E17–E24 ok означает выполненный запрос: фактические ряды и их время надо смотреть в данных проверки.

## Восстановить ответы модели

1. В окне анализа выберите **«Локальная LLM напрямую»**, нажмите **«Проверить ИИ»**, затем «Причины» или «Последствия». Так можно использовать существующий vLLM без Astra AI. Обновление движка окна начинает новый диалог; глобальные настройки источников не меняются. Автоматического скрытого fallback нет.
2. Если локальный тест не проходит, в глобальных настройках проверьте фактический OpenAI-compatible URL vLLM и served model ID. Ранее использовались `http://127.0.0.1:8002/v1` и `qwen`; они не считаются подтверждёнными для любой установки. Наличие `/models` не доказывает успешную генерацию: нужна «Проверка ответа».
3. Для Astra AI в настройках Peoplehub нужен полный наблюдённый URL `http://10.128.77.23/api/v1/settings/ai/request/chat/completions`, model `qwen` и действующий Bearer token **для AI endpoint**. Сверьте с реальным запросом вашего браузера и поддерживаемым контрактом вашей версии Astra.
4. При 403 проверьте роль/разрешение AI, поддерживаемую сервисную авторизацию и правила reverse proxy. Обновление Pulse не даёт дополнительных прав Astra. Учётные данные вводятся в настройки; Authorization/Cookie/HAR в чат не передаются.

Даже успешно завершённый ответ проверяется по UID и E##. Для известной ошибки доказана причина завершения: `EmptyDir data` превысил `1Gi`. Причина роста файлов, фактическая потеря данных и простой всего сервиса пока не установлены. Готовность замены надо проверять по Pod владельца и endpoints; суммарный Failed Pod не доказывает отказ всего приложения.

## Подключить реальные логи Astra

В текущем адаптере используется POST `/api/v1/logs/search/monitorLogs` с time/query/paging. Этот контракт требует проверки для вашей версии Astra. Наблюдавшийся в браузере `filter_preview` может иметь другой путь, Payload и формат ответа; считать интеграцию уже совместимой нельзя.

1. Раскройте E16 и посмотрите точный текст ошибки. 401/403, 404, несовместимый ответ и пустой результат требуют разных действий.
2. На странице логов Astra откройте DevTools → Network → Fetch/XHR. Для запроса `filter_preview` сохраните **Request URL, HTTP-метод и обезличенный Payload**, без Authorization и Cookie. Пример ответа с названиями полей также помогает проверить адаптер.
3. Укажите реальные поля привязки. В присланном примере присутствуют `labels.pod_namespace` и `labels.pod_name`. Отдельного поля кластера в том примере нет. Его нельзя выдумать: нужен настоящий cluster label или подтверждённое ограничение по источнику/группе, которое надо поддержать в адаптере. Иначе можно получить журналы другого кластера с тем же namespace/pod.
4. В настройках Astra теперь читаются обратно сохранённые URL/поля, но не токен. После настройки сверяйте E16 с теми же логами в Astra. Для старого удалённого Pod нельзя приписывать журналы нового UID одному лишь совпадению имени.

## Дашборды

- В Обзоре нажмите CPU, RAM или диски: откроется подробный экран ресурса. Используйте интервалы 1/6/24 часа. История появляется только там, где её хранит источник; отсутствие истории не заменяется синтетическим графиком.
- Нажмите «Узлы Ready» или «Сведения»: версии API/kubelet, состав/ресурсы узлов, requests/limits и условия. Резервирование — бюджет планирования, не фактическая утилизация.
- Workloads и список проблем ведут к объектам и расследованию. Пик отдельного узла и общий процент кластера — разные показатели.
- В настройках Peoplehub → метрики проверьте сохранённый источник. Для подтверждённой схемы: Kubernetes API, `monitoring/kube-prom-kube-prometheus-prometheus:9090`, dedicated. Reader должен иметь чтение nodes/pods и `get services/proxy`. Новый токен нужно заменять/ротировать до фактического expiry.

Произвольный конструктор дашбордов и графики логов Astra этим выпуском не добавляются. Для таких панелей сначала нужен проверенный контракт реальных данных и согласованный набор показателей.

## Qdrant и документация

`Qdrant не настроен` означает отсутствие активной векторной базы, а не готовый поиск bge-m3. Если нужен локальный комплект, выполните на сервере из каталога действующего выпуска:

```bash
pulse_runtime="$(docker inspect pulse-clusters-8090-pulse-1 --format '{{range .Mounts}}{{if eq .Destination "/runtime"}}{{.Source}}{{end}}{{end}}')"
python3 scripts/pulse-services.py --runtime "$pulse_runtime" knowledge-start
python3 scripts/pulse-services.py --runtime "$pulse_runtime" knowledge-model
python3 scripts/pulse-services.py --runtime "$pulse_runtime" knowledge-check
./pulse --runtime "$pulse_runtime" start-offline
```

Команды запускают отдельные Qdrant/Ollama и загружают веса embeddings; нужны место на диске, ресурсы и доступ к реестрам/модели. Существующие внешние endpoints надо проверить по [AI-KNOWLEDGE-RU](AI-KNOWLEDGE-RU.md), а не заменять вслепую.

После готовности импортируйте встроенный корпус Kubernetes 1.30 по инструкции AI-KNOWLEDGE-RU и проверьте хотя бы один результат поиска с source/version. Версия соответствует API Peoplehub 1.30.8. Документация VK Teams требует отдельной официальной выгрузки/импорта и отчёта покрытия; пустой или JS-only сайт не считается загруженной документацией.

## Новый пустой диалог

Каждое открытие ✧, «Новый диалог» и повторный вход через пункт «Чат с ИИ» создаёт новую сессию. Закрытие удаляет её из памяти Pulse. Предыдущие решения инцидентов автоматически в такие диалоги не подмешиваются. Внутри одного открытого диалога уточнения продолжают текущую переписку. Документация и текущие данные кластера остаются доступным контекстом; история на стороне внешнего провайдера регулируется отдельно.
