# Проверки Pulse Clusters 0.9.0

Проверено 30 октября 2026 в текущей облачной среде Linux amd64 / Python 3.12.

- **136 passed** в pytest; тесты не пропущены. Один warning Starlette TestClient об устаревающем httpx-адаптере.
- Проверены выборка более 40 проблем, фильтры, страницы и изоляция кластеров; контекст вопроса, продолжение после исчезновения сигнала, сохранение истории за пределами 100 чужих заданий.
- Проверены сохранение шифрования/истории при миграции схемы, проверка UID Pod до и после чтения логов, allowlist метрик, контракт Holmes, отказ лишних tools, отдельные cluster tokens и непредсказуемый challenge.
- Docker Pulse 0.9.0 собран с закреплёнными хешами из wheelhouse; действующий контейнер отвечает `/healthz` и защищённому `/api/overview`.
- На отдельном Docker-стенде проверен реальный переход 0.8.0 → CLI backup/restore → 0.9.0: сохранены пароль, ключ шифрования, подключение, настройки qwen, документ и прежнее расследование. Стенд использовал тестовые данные, не runtime пользователя.
- Три Chromium-сценария: `ui-smoke.py` проверяет реальные авторизованные API и операции с документами/настройками; `dashboard-ui-smoke.py` и `compact-ui-smoke.py` проверяют представление на явно заданных тестовых ответах API.
- Браузер подтвердил один экран на 1920×1080 и 1366×768, ряды 3/3/7, подробный dashboard, 80 проблем с пагинацией, две реплики контекстного чата, безопасный вывод текста и отсутствие горизонтальной прокрутки на mobile. Ошибок JavaScript нет.

Скриншоты и пошаговое обновление: [UPDATE-0.9.0-RU](UPDATE-0.9.0-RU.md). Источники Kubernetes/Prometheus/Astra и vLLM пользователя здесь не подключены. **Реальный Holmes-контейнер не запускался:** registry вернул Forbidden. Протокол сопоставлен с официальным исходным tag 0.45.0; mocks не доказывают работу образа или tool calling вашей модели. Порядок живой приёмки: [HOLMES-RU](HOLMES-RU.md).

GitHub Actions, production-нагрузка и точность диагнозов в вашем контуре отдельно не подтверждались. `/healthz` подтверждает работу Pulse, а не исправность всех подключений.

## Исторический отчёт 0.6.1


Проверено 29 октября 2026 в Linux amd64 / Python 3.12.14, Docker Engine 28.4.0. Это самостоятельная реализация; результат «158 тестов» из прежних документов не относится к этому выпуску.

- `python -m pytest -q`: **84 passed**, один warning об устаревающем httpx-адаптере Starlette TestClient; тесты не пропущены.
- Установка закреплённых зависимостей с `--require-hashes`: успешна.
- pip-audit закреплённых runtime-зависимостей, выполненный 27 октября: известных уязвимостей не обнаружено на момент проверки. Это не полный аудит приложения.
- Docker image собран с зависимостями из локального wheelhouse с проверкой хешей, стартует непривилегированным пользователем с read-only filesystem и отдельным runtime.
- `/healthz` возвращает 0.6.1, защищённый `/api/overview` отвечает после авторизации; начальная панель пустая.
- Реальный Chromium через `scripts/ui-smoke.py`: навигация, загрузка/поиск/удаление документа, безопасный вывод текста, сохранение настроек, проверка ID кластера, desktop/mobile, отсутствие ошибок JavaScript. Проверка нашла и помогла исправить HTML pattern ID.
- CLI backup действующего тестового Docker runtime, остановка и последующий запуск: успешны. Restore и повторный запуск проверяются на том же одноразовом стенде; резервные копии в поставку не включены.
- Unit/API tests покрывают auth/CSRF, шифрование подключений, обработку URL, scope поиска, ограничения очереди, перезапуск заданий, блокировку второго процесса, отказ опасных архивов и адаптеры внешних источников на mock-ответах.

**Не проверено:** ваш Kubernetes, маршрутизация, реальные Astra API/labels, GPU и vLLM/веса, качество ответов конкретной модели, production-нагрузка, другая архитектура процессора и GitHub Actions (workflow добавлен, его облачный результат отдельно не наблюдался).

Контрольный запуск на сервере: `./pulse check`, затем сопоставление инвентаря с kubectl, выборочные логи/метрики и расследование известного тестового случая. `/healthz` сам по себе не подтверждает исправность внешних источников.
