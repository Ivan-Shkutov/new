# Дополнения к установке 0.5.0

Это рекомендации к переданным документам, не отчёт о выполненной установке. Исходные инструкции сохранены в `../imported/0.5.0/`. Команды Pulse пока не доступны в репозитории и не проверены здесь.

## 1. Проверять поставку до исполнения её скриптов

START-HERE предлагает распаковать архив от root и затем запустить `./pulse verify`. Такая проверка выполняет код из ещё не проверенной поставки. Внутренний manifest полезен, но не заменяет внешнюю проверку до распаковки и исполнения.

Предлагаемый порядок:

1. Получить архив и ожидаемую SHA256 через доверенный канал. Проверить, что checksum относится к нужной версии и имени файла.
2. Вычислить SHA256 архива и сравнить с ожидаемой. Не создавать «ожидаемый» checksum из самого полученного архива.
3. Просмотреть состав архива без выполнения скриптов. Проверить абсолютные/выходящие за каталог пути, symlink/hardlink, специальные файлы и ожидаемый размер после распаковки. Один просмотр списка не является автоматической полной проверкой безопасности.
4. Распаковать проверенный архив непривилегированным пользователем в новый staging-каталог с ограничениями ресурсов; не поверх старого runtime и не прямо поверх Git checkout.
5. Проверить manifest и изучить установочные команды. Только после этого готовить `/opt` и выполнять необходимые привилегированные операции.

Для воспроизводимой установки дополнительно зафиксировать digest базового образа через уже описанную переменную `PYTHON_BASE_IMAGE`. Не придумывать digest и не отключать TLS/проверку хешей при сбоях.

## 2. Разделить проверки готовности

| Проверка | Что подтверждает |
|---|---|
| healthz | Процесс отвечает; точный контракт нужно проверить в коде |
| Инвентарь Kubernetes | Чтение API, coverage, актуальность и корректные статусы |
| Метрики/логи/инциденты | Доступность и полноту каждого источника отдельно |
| Tool calling | Работу протокола вызова инструментов |
| Известный инцидент | Качество диагностики на конкретном случае |
| Restore на пустой установке | Пригодность резервной копии к восстановлению |

Не превращать отсутствие необязательной PVC usage в общий вывод «приложение не работает». В инструкции следует явно перечислить обязательные источники конкретного пилота и допустимые ограниченные режимы. Изменять поведение `check` можно только после изучения кода и ожиданий CI/операторов.

## 3. Миграция требует сверки результата

Оставить требование import до первого запуска и остановки старой панели для согласованной копии. Добавить сравнение числа записей истории, документов и подключений до/после, выборочную проверку содержимого, расшифрования credentials и прав доступа. Проверить, что незавершённые задания не запустились заново. Секреты в отчёт не включать.

До открытия новой панели на запись определить точку отката: новые записи 0.5.0, согласно документации, автоматически назад не переносятся. Старый runtime и backup хранить до завершения приёмки.

## 4. Backup хранит ключ вместе с данными

Сохранение registry.key нужно для восстановления, но его наличие рядом с зашифрованными подключениями означает, что украденная копия может раскрыть credentials. Использовать защищённое хранилище и шифрование резервных копий с отдельным управлением доступом к ключам. Не добавлять runtime/backup в Git даже в приватном репозитории.

## 5. Граница Windows/Linux

PowerShell в инструкции используется для передачи файлов и SSH-туннеля. Целевой runtime описан для Linux amd64 с host networking и CPython 3.12 wheels. Это не подтверждённый сценарий локального запуска в Windows Docker Desktop или ARM. Python 3.10+ на хосте и Python 3.12 в контейнере — разные требования, а не сами по себе противоречие.

## 6. Контроль изменений

После импорта исходников уточнить ignore правила под реальную структуру. `.gitignore` уменьшает случайные добавления файлов, но не удаляет ранее отслеживаемые секреты и не заменяет проверку содержимого коммита. Тестовые публичные сертификаты или fixtures при необходимости добавлять точечными исключениями после проверки.
