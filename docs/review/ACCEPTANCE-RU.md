# План приёмки и работа через GitHub

Все сценарии приложения ниже имеют статус **не выполнено**. Таблица задаёт ожидаемые доказательства; она не является отчётом QA.

## Этапы

1. **Импорт.** Получить archive + checksum, проверить пути/типы/размеры, исключить runtime и реальные credentials, сохранить чистый источник версии 0.5.0. Сопоставить архив с документами и MANIFEST. Wheelhouse и крупные релизные артефакты хранить выбранным способом отдельно от повседневных изменений исходников; способ выбрать после осмотра поставки.
2. **Базовое воспроизведение.** Прочитать AGENTS/README, manifests, lockfiles, CI и `docs/QA-RU.md`. Установить зафиксированные зависимости с сохранением проверки хешей. Воспроизвести заявленные тесты, сохранить точные passed/failed/skipped и exit status, команды и версии среды. Не считать 0 тестов успехом.
3. **Изолированная установка.** Выполнить настоящую сборку контейнера, запуск и HTTP/браузерную проверку, повторный init/start и offline путь. Проверить один API-процесс, права файлов и отсутствие необходимости Docker socket в приложении.
4. **Исправления.** Для каждого подтверждённого дефекта — воспроизводимый пример, минимальное исправление и регрессионный тест при необходимости. Документировать причину; не выдавать предполагаемый риск за исправленную ошибку.
5. **Пилот.** Один кластер с ограниченными правами, затем второй с совпадающими именами объектов для проверки изоляции. Реальные Astra/vLLM проверять только через предоставленный доступ; значения credentials хранить вне Git и чата.

## Матрица обязательных проверок

| ID | Сценарий | Критерий прохождения |
|---|---|---|
| ENV-01 | Clean build/start | Контейнер работает, API и UI отвечают, зависимости воспроизводимы |
| ENV-02 | Повторные init/start | Пароли, env, документы и история не перезаписываются |
| ENV-03 | Offline start | Нет pull/download; все требуемые артефакты заранее учтены |
| AUTH-01 | admin/operator/viewer | Сервер отклоняет запрещённые действия независимо от UI |
| AUTH-02 | Cross-cluster IDs | Нет чужих объектов, логов, документов, чатов, заданий и tools |
| AUTH-03 | Секреты и вывод | Credentials отсутствуют в ответах, ошибках, логах и LLM-контексте |
| AUTH-04 | Недоверенный контент | Нет XSS; инструкции в логах/документах не расширяют полномочия tools |
| K8S-01 | Инвентарь/пагинация | Согласуется с контрольным API-снимком с учётом времени сбора |
| K8S-02 | 403/429/timeout | Coverage/stale видны; один отказ не блокирует другие кластеры |
| MET-01 | Отсутствующая метрика | Отображается отсутствие данных, а не нулевое потребление |
| AST-01 | Совпадающие имена в кластерах | Точная изоляция логов и инцидентов, в том числе при пагинации |
| AST-02 | Лимит/ошибка источника | Неполнота явно показана; проблема не объявляется решённой |
| LLM-01 | Настоящий tool-call round trip | Модель использует результат инструмента, scope задаётся сервером |
| LLM-02 | Loop/timeout/restart | Ограничения работают; нет бесконечного цикла и скрытого повторного задания |
| LLM-03 | Известный инцидент | Причина опирается на факты; альтернативы и недостающие сведения обозначены |
| RAG-01 | scope/version/archive | Чужие, исключённые по версии и архивные документы не попадают в выдачу |
| RAG-02 | Неподходящий/большой файл | Ограниченное потребление ресурсов и понятная ошибка индексации |
| DATA-01 | Import runtime-v3 | Исходник сохранён; история/документы сверены; задания не повторены |
| DATA-02 | Backup → empty restore | Данные и credentials восстановимы, старая сессия не принимается |
| DATA-03 | Повреждённый архив/ошибка диска | Отказ без уничтожения рабочего runtime и записи вне назначения |
| LOAD-01 | Согласованная нагрузка пилота | Измерены длительность polling, latency UI, очередь, RAM/CPU/диск |

Для LOAD-01 сначала согласовать число кластеров/объектов/пользователей и допустимую задержку. Не объявлять произвольные пороги гарантированной производительностью. Фиксировать временной интервал, p95 и максимумы, условия и частоту ошибок.

## Формат доказательства

Для каждого запуска сохранять commit SHA, конфигурацию без секретов, версии runtime/образов/модели, команду, время, exit status и итог. Раздельно учитывать passed, failed, skipped и unrun. Логи предварительно очищать от credentials и пользовательских данных. CI для первых этапов может работать на fixtures; живые проверки интеграций должны быть обозначены отдельно.

## Организация разработки

Использовать существующий checkout изолированной облачной задачи; дополнительные worktrees без необходимости не создавать. Работать тематическими ветками и проверяемыми коммитами, результаты собирать в PR. Сохранённая ветка не равна слитому main или установленному приложению. Не отправлять на GitHub runtime, kubeconfig, registry.key, базы истории и backup.

В первую очередь обеспечить один подтверждённый базовый путь. Дополнительные адаптеры не должны блокировать развитие основного сценария, но их непроверенный статус должен оставаться видимым.
